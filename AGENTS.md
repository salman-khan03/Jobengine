# AGENTS.md

## Product

This repository is RoleRadar, built on top of JobEngine's ingest/sponsorship
pipeline. RoleRadar is an evidence-grounded job recommendation and
application-tracking platform for job seekers. Full design rationale:
[`docs/roleradar.md`](docs/roleradar.md). Architecture: [`docs/architecture.md`](docs/architecture.md).

## Critical domain rule

Never collapse these concepts:

1. **recommendation** — RoleRadar's prediction (`rr_decisions`: score, verdict,
   confidence, cited evidence, `model_version`). Despite the table name, this
   is the *recommendation*, not the user's decision.
2. **decision** — the user's APPLY / SAVE / SKIP / DEFER choice.
3. **application** — an actual job application (applied_at, source, url,
   current stage).
4. **application event** — immutable progression history for one application.
5. **feedback** — the user's assessment of a recommendation's relevance.

As of 2026-09-11, all five are implemented as distinct tables in
[`src/roleradar/store.py`](src/roleradar/store.py): `rr_decisions`,
`job_decisions`, `rr_applications`, `rr_application_events` (append-only —
no update/delete function exists for it, enforced by a test), and
`recommendation_feedback`, plus `rr_analytics_events` for product-funnel
events. The legacy `rr_outcomes` table (which used to conflate "user
decision" and "post-application progress" into one flat log) was retired in
this migration — `record_outcome`/`scored_outcomes`/`funnel_counts` keep
their old signatures for CLI/API back-compat but are now backed by
`rr_applications`/`rr_application_events`. See
[`docs/roleradar.md`](docs/roleradar.md#the-decision--application--feedback-loop-kept-apart-on-purpose)
and the README's "Five decisions worth defending in an interview" section.

JobEngine's older manual tracker (`applications` + `status_events` in
[`src/jobengine/db.py`](src/jobengine/db.py)) is a separate, still-live
feature (the pre-RoleRadar CLI/HTTP application tracker) that proved the
immutable-append-log pattern this migration reused for
`rr_application_events` — the two are intentionally not merged, since
JobEngine's tracker predates RoleRadar's decision layer and has its own
frontend/API consumers.

## Engineering rules

- Run tests before and after changes.
- Do not delete tests to make CI pass.
- Do not fabricate metrics or users. No latency/throughput/user/adoption
  figure goes into docs until a real run in this repo produced it — see
  `docs/known-limitations.md` and `docs/roleradar.md` §5 for the standing
  precedent (evaluation harness is built and tested; no real outcome metrics
  exist yet, and none are to be invented).
- Do not add résumé/candidate claims unsupported by candidate evidence —
  `explain.validate_grounding` is the enforcement point; do not weaken it.
- Database changes require migrations. This repo has no formal migration
  tool — tables are SQLAlchemy `Table` objects registered on the shared
  `jobengine.db.metadata`, created via `metadata.create_all()`
  (`init_db()`). A schema change means: add/alter the `Table` definition,
  keep it additive/backward-compatible where existing rows must survive, and
  say so explicitly in the PR/summary — there is no autogenerated migration
  diff to check.
- Product actions must persist server-side. Do not implement Apply/Save/
  Skip/Defer, stage changes, or feedback as local-only React state.
- Application history is immutable — never `UPDATE` or `DELETE` an
  application-event row; append a new one.
- Every recommendation must be reproducible/versioned
  (`store.model_version()` — keep this in sync with any ranking-weight
  change).
- All AI-generated factual claims must have evidence (`explain.py`'s
  citation + numeric-grounding checks).
- Prefer typed structured outputs over free-form parsing.
- Use a single DB transaction for state-transition + event-record writes
  (see `store.record_outcome()` for the existing pattern: row lookup with
  `with_for_update()`, then insert, all inside one `engine.begin()` block).
- Never commit credentials or API keys. Secrets go in `.env` (see
  `.env.example`), which is git-ignored.
- This repo is currently **not** a git repository (`git status` reports "not
  a git repository"). Confirm with the user before assuming any git workflow
  (branches, commits, PRs) is in play.

## Architecture

Frontend: Next.js 16 + React 19 + TypeScript (`web/`)

Public search API: Spring Boot 3 / Java 21, Redis-cached (`services/core-api/`)

Primary workflow API + RoleRadar decision engine: FastAPI (Python), mounted
at `/api` (JobEngine) and `/api/v2` (RoleRadar) — `src/jobengine/`,
`src/roleradar/`

Database: PostgreSQL in production (pgvector extension available), SQLite
for local dev/tests via `DATABASE_URL`

Cache: Redis (Upstash-compatible), used by the Spring Boot search path

Infra-as-code (written, not applied): Terraform EventBridge → Lambda → SQS →
worker + CloudWatch (`infra/`)

## Definition of done

A task is not complete until:

- implementation exists
- tests pass (`pytest -q`, and `npm run build` for frontend changes)
- type checking passes (`mypy ...`)
- lint passes (`ruff check ...`, `npm run lint` for frontend changes)
- error states are handled
- documentation is updated when architecture changes (`docs/architecture.md`,
  `docs/database.md`, `docs/roleradar.md`, and this file where the domain
  model or commands change)
